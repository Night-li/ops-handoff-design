# 03 · 故障排查（按症状查）

> 原则：**先看日志，再动手**。
> 启动日志在 `$DSH_HOME/logs/`，文件名形如 `startup-<时间戳>-<uuid>.log`（每次启动一份，失败的那份会明确写"哪些插件没起来、缺什么服务"）。
> 服务运行中的输出在**你启动它的那个终端**里，别关那个窗口。

## A. 浏览器打不开、白屏或一直转圈

**先分清是哪一层**（30 秒判据）：

```powershell
# ① 进程在不在
Get-NetTCPConnection -LocalPort 3080 -State Listen | Select-Object OwningProcess
# ② 服务答不答
curl.exe -s -o NUL -w "%{http_code}`n" http://127.0.0.1:3080/
```

| ① | ② | 结论 |
|---|---|---|
| 空 | —— | 服务没起来 → 看 [E](#e-dsh-web-起不来) |
| 有 | `401` | 服务正常，**你少了 token** → 看 [B](#b-401-与-403两种完全不同的拒绝) |
| 有 | `200` 但页面白 | 前端加载问题 → 硬刷新 `Ctrl+Shift+R`；仍白则开 DevTools Console 看第一条红错 |

**前端白屏的三个常见真因**：

1. **插件的前端模块加载了但没注册**。Console 里会出现 `... loaded without registering ... via __ModuleLoader__`。这说明包名与模块登记 id 不一致——装的是新版、包的 `lib/client.js` 里写的是旧 id。**处置**：升级/换版本；验证方式见 [C](#c-侧边栏没有任务看板)。
2. **浏览器缓存**。硬刷新；或换一个无痕窗口试一次（无痕能开就是缓存问题）。
3. **同 origin 开了第二个 DSH 页面**。HTTP/1.1 连接池被打满会让整站转圈，**完全退出浏览器再重开**（不是刷新）。

## B. 401 与 403：两种完全不同的拒绝

| 拿到 | 含义 | 处置 |
|---|---|---|
| **401** | "你是谁？"——没带 token / cookie | 用终端打印的 `http://127.0.0.1:3080/?token=...` 打开一次（会种 cookie）。token **一次性** |
| **403** `{"ok":false,"error":"forbidden"}` | "你怎么来的？"——缺同源栅栏头 | 请求带 `sec-fetch-site: same-origin` |

**实测两条**：

- 裸 `GET /api/task-board/state`（无任何头）⇒ `403 forbidden`；
- 加上 `sec-fetch-site: same-origin` ⇒ `200`，**即使不带 cookie**。

> 反过来说：403 与 cookie 无关，别去翻登录状态。

## C. 侧边栏没有「任务看板」

按这个顺序（每一步都有明确判据，别跳）：

1. **包在不在**：
   ```powershell
   dsh --profile web --dump-config | Select-String "ui-task-board-local"
   ```
   没输出 ⇒ 没装/没进 bundles → 回 00 手册 §2.2。
   有输出 ⇒ 往下。
2. **服务是不是改完才起的**：`--dump-config` 现读文件，**运行中的进程不会变**。改完必须重启（关掉 `dsh web` 再起）。
3. **前端模块有没有 404**：
   ```powershell
   # 打开页面 → DevTools → Network → 过滤 "plugins/" → 看有没有 404
   ```
   或直接抓首页 HTML 找 `__DSH_BOOT__` 里这个插件的 `url` 字段，再单独访问它。
4. **模块 id 是否与包名一致**（[A](#a-浏览器打不开白屏或一直转圈) 第 1 条）。这是"HTTP 200 但界面没有"的典型形态——**端点通 ≠ 挂上了**。

## D. 装了但没生效

三类原因，按顺序排（**80% 是第 1 条**）：

| # | 判据 | 处置 |
|---|---|---|
| 1 | 安装时的输出里有没有 `declares no dsh.bundle — installed as a plain dependency, not a profile layer` | 有 ⇒ 它需要**手写 patch**（`insert`），见 00 手册 §2.7 / 02 样例 |
| 2 | 改完配置后重启过没有 | 没重启 ⇒ 重启；`--dump-config` 能看到不代表运行中生效 |
| 3 | 浏览器硬刷新过没有 | 没 ⇒ `Ctrl+Shift+R`；还不行用无痕窗口排除缓存 |

> 反过来：`bundles` 里如果混进了一个**没有 `dsh.bundle`** 的包，启动会**直接崩**（`declares no dsh.bundle in its package.json`）。这是"装完起不来"的头号原因。

## E. `dsh web` 起不来

### E1 · 端口被占

```
startup failed: 2 required plugins did not activate
Failed plugins (1):
  webserver (required)
    Error: listen EADDRINUSE: address already in use 127.0.0.1:3095
```

**注意这段日志的第 2 层信息**：后面还会列 "Plugins waiting for services"，把 `ui-task-board-local → webServer` 这类依赖链全列出来。**它们是连带的，不是元凶**——只有第一条 `Error:` 是真的。

处置（**按端口精确杀，绝不加 `/T`**）：

```powershell
Get-NetTCPConnection -LocalPort 3095 -State Listen | Select-Object OwningProcess
taskkill /PID <上面的PID> /F
```

> ⚠️ 别顺手杀 3080 的进程——那是你的主实例。

### E2 · 启动崩在插件加载

看 `$DSH_HOME/logs/startup-*.log` 的**最新一份**，找第一行 `Error:`。常见三种：

| 日志特征 | 原因 | 处置 |
|---|---|---|
| `declares no dsh.bundle in its package.json` | 把只有 client 的包塞进了 bundles | 从 `bundles` 移除，改走 patch `insert` |
| `duplicate loader entry id: xxx` | patch 里的 id 与某个 bundle 里的 id 撞了 | `--dump-config | Select-String "<id>"` 找到两处，改掉自己的 |
| `Cannot find module '@deepseek-ai/xxx'` | 主包与插件版本不匹配（peer 断裂） | 回 [F](#f-安装被拒兼容性闸)；或换兼容版本 |

### E3 · 换了 `DSH_HOME` 之后起不来

新 home 是**空的**：没有 profile、没有凭据、没有会话。先按 00 手册 §3.1 走一遍（`dsh plugin add` 会自动 `initialized profile web at ...`），再 `dsh web`。

## F. 安装被拒（兼容性闸）

```
dsh: installation rejected: Plugin <pkg>@<ver> is incompatible with dsh <ver>: peerDependencies {...}
Running it may cause crashes or data loss.
```

这是宿主的**主动保护**，不是网络或权限问题。三条路，按推荐顺序：

1. **换一个声明的 peer 区间覆盖你主包版本的版本**（最干净）。先看有没有：`npm view <pkg> versions --json`。
2. **跳过它**——如果这个包只是"锦上添花"。
3. **显式接受风险**（明确知道后果时）：
   ```powershell
   dsh plugin --profile web allow-version <pkg>@<ver> --dsh-version <你的主包版本> --accept-risk
   dsh plugin --profile web add <pkg>
   ```
   放行记录在 `profiles/web/compatibility.json`，**只对这一对精确版本有效**，主包一升级就得重放。

> 实测案例：`dsh-memory@0.1.0` vs 主包 `0.2.0-rc.2`。放行后能装、能起、库能建（隔离实测），但**这属于"风险自担"**，生产环境请等插件官方跟进。

## G. 看板相关的三种"空"与失灵

### G1 · 看板 0 张卡

正常（新装就是 0 张）。判据：

```powershell
node check-board.mjs http://127.0.0.1:3080 "<token>"
# GET /state => 200 cards=0
```

如果 `POST /action` 之后还是 0，看**这一步的返回体**：`200` 且 `tasks` 里有你那张 = 建成功了，只是前端没刷新；`400 invalid-action` = 你的 payload 结构不对（字段要求：`{requestId, action:{kind:'create', id, input:{title, description, prompt}}}`）。

### G2 · 账本被锁

```
task-board ledger is already owned by process <pid>
```

有另一个进程持有 `task-board/ledger-v2.lock`。

```powershell
Get-NetTCPConnection -LocalPort 3080 -State Listen | Select-Object OwningProcess   # 先确认只有一个实例
```
确认没有活着的实例后再删锁（`Remove-Item "$env:USERPROFILE\.dsh\task-board\ledger-v2.lock"`）。**两个实例同时开着时删锁 = 数据互相覆盖。**

### G3 · 点执行，卡片直接 `failed`

最常见原因是**执行会话起不来**，不是看板坏了。看执行会话的日志/侧边栏里那条新会话：

- 报 `workspace not found` ⇒ 卡里写死了一个本机不存在的 `workspaceId`。**处置**：把卡的 `workspaceId` 留空（新环境推荐留空，跨机也能用）。
- 报 `apiProxy service is unavailable` ⇒ 宿主这条线缺执行通道（多见于版本不匹配）。**处置**：升级/降级到兼容版本，或先只用手工卡（不靠"执行"）。

## H. 记忆存不进去或召不回来

按链路拆四段查，**别一上来就怀疑模型**：

| 段 | 判据 | 不过时怎么办 |
|---|---|---|
| ① 插件挂上没有 | `dsh --profile web --dump-config \| Select-String "^- id: memory"` | 回 00 手册 §2.3 |
| ② 库建出来没有 | `Test-Path "$env:USERPROFILE\.dsh\memory\memory.db"` ⇒ `True` | 起过一次服务就该有；没有说明插件没激活 |
| ③ 库里有没有东西 | `node memory-db-tools\list-memory-summary.mjs` ⇒ `TOTAL: N` | `N=0` ⇒ 没人写过记忆（不是坏了） |
| ④ 模型能不能读到 | 新会话里问「上次让你记的 X 是什么」 | 只有这一段需要模型 key |

**实测的两种"假故障"**：

- `list-memory-summary.mjs` 报 `ERR_SQLITE_ERROR: unable to open database file` = **库还不存在**（不是权限）。先把服务起一次。
- 记忆工具跑出来 `TOTAL: 0` 但你觉得写过 —— 你可能换了 `DSH_HOME`，看的是另一个 home 的库。

> `memory.db` 有三个文件（`.db` / `-wal` / `-shm`）。**只搬 `.db` 会丢最近写入**（还在 WAL 里）。

## I. `--help` 不生效、甚至直接执行

**这不是故障，是这些脚本的行为**。实测两例：

```powershell
# ① 不认 --help，直接执行了一次归档扫描
dsh-archive-inactive --help
=== 归档扫描 ===
条件: >48h 未活跃 且 尾部无未闭合turn
模式: 实际移动
待归档会话目录: 0 个，共 0.0 MB          ← 它真的跑了

# ② 先连服务（默认 3080），连不上才轮到 --help
dsh-context-check --help
查询失败：unexpected response shape
（需要 DSH web 在 http://127.0.0.1:3080 运行）
```

**规矩**：

1. 跑一个不熟的脚本之前，**先读它源码头部的参数解析**（`Select-String -Path <file> -Pattern "argv|has\("`）。
2. 移动/删除/批量类脚本，**先找 `--dry-run`**，没有就别跑。
3. 换端口/换机器时，会话工具的连接地址用环境变量给：`$env:DSH_WEB_URL = "http://127.0.0.1:3095"`。

## J. 中文乱码与 BOM

| 场景 | 症状 | 处置 |
|---|---|---|
| `cordis.patch.yml` / `package.json` 被写进 BOM | 启动报 YAML/JSON 解析错；首行注释被吞 | 用 `Out-File -Encoding utf8NoBOM` 或 Node `fs.writeFileSync(p, t, 'utf8')`；**别用 PS 5.1 的 `Set-Content -Encoding UTF8`** |
| `.cmd` / `.bat` 里有中文 | 命令被拆坏、报奇怪的"不是内部或外部命令" | 脚本一律纯 ASCII |
| PowerShell 里跑 Node，中文输出乱码 | 控制台是 GBK、Node 输出 UTF-8 | 先 `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)` |
| 管道截断 Node 输出 | 进程被提前杀掉 / 输出只剩前几行 | 先全量捕获再 `Select-Object`（`Select-Object -First N` 会掐断管道） |

## K. 什么时候该"推倒重来"

不要在没有证据的情况下删 `node_modules`。**重来的最小动作**：

```powershell
# ① 只摘掉出问题的那个包
#    —— 改 profiles/web/package.json：删依赖行 + 删 bundles 里对应项
# ② 重新装
dsh plugin --profile web add <包名>
# ③ 还不行，再整体重建 profile（会丢 patch 层，先备份 cordis.patch.yml）
```

**永远先备份** `profiles/web/package.json` 与 `cordis.patch.yml`——它们是纯文本、只有几 KB，但重建成本最高。
